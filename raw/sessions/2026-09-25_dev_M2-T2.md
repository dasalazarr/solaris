# 2026-09-25 · dev · M2-T2 — Esquema RAG

## Tarea
M2-T2: esquema RAG (documents, chunks, folder_acl, fmea_rows) con filtrado ACL en SQL, runner de
migraciones y tests de inserción y consulta por rol. Diseñado para servir a M2-T3 (ingesta),
M2-T4 (AMFE), M2-T5 (recuperación híbrida) y M2-T6 (citas).

## Cambios
- `app/backend/migrations/001_rag.sql`: esquema `rag`.
  - `folder_acl(folder, role)` PK compuesta, con CHECK de formato.
  - `documents` PK (doc_id, version), `UNIQUE (doc_id, version, folder)`, `sha256` validado y GIN sobre `part_refs`.
  - `chunks`: identity id, `chunk_no` (UNIQUE por doc/versión para una ingesta idempotente), `page`, `section`, `content`,
    `tsv` generado con `'simple'`, `embedding vector(1024)` que admite NULL y `folder` desnormalizado.
    FK compuesta (doc_id, version, folder) → documents con ON UPDATE/DELETE CASCADE: el folder
    desnormalizado no puede divergir del documento, y un cambio de carpeta en un re-sync se propaga.
  - `fmea_rows`: columnas de F03 con S/O/D en smallint 1–10 (NULL si el AMFE sucio no cuadra), `rpn`,
    `raw jsonb NOT NULL`, más `folder` con la misma FK compuesta (las filas AMFE también tienen ACL).
  - Índices: HNSW `vector_cosine_ops` sobre embedding, GIN sobre tsv y btree sobre folder y (doc_id, version).
  - `rag.visible_chunks(role)` y `rag.visible_fmea_rows(role)`: `LANGUAGE sql STABLE`, sin SECURITY
    DEFINER; con deny-by-default. EXPLAIN confirma que el planificador las inlinea: primero el join con
    folder_acl filtrado por rol y después el Sort/Limit por distancia (filtro antes del ranking).
- `solaris/db/__init__.py`: `connect()` desde Settings (DATABASE_URL o piezas del compose; la contraseña
  se pasa como kwarg, nunca en URL).
- `solaris/db/migrate.py`: runner (orden por nombre `NNN_*.sql`, `rag.schema_migrations` con sha256,
  `pg_advisory_xact_lock`, una transacción por migración y aborto si cambia una migración ya aplicada, `--dry-run`).
- `solaris/rag/acl.py`: `load_folder_acl()` (valida roles declarados) y `sync_folder_acl()` (reemplaza
  la tabla en una transacción, de modo que las revocaciones se reflejan en el re-sync). acl.json solo se lee.
- `solaris/settings.py`: `database_url` pasa a SecretStr y se añaden postgres_host, solaris_db_port,
  postgres_user, postgres_db, postgres_password y db_connect_timeout_s.
- `pyproject.toml`/`uv.lock`: `psycopg[binary]>=3.2` (3.3.6).
- `tests/test_rag_schema.py`: 12 tests (3 sin BD y 9 con BD en `transaction(force_rollback=True)`).

## Decisiones
- **vector(1024)**: dimensión nativa de BGE-M3 y multilingual-e5-large (candidatos multilingües ES/EN).
  Por debajo del límite HNSW de 2000. Cambiar de modelo implica una migración nueva y re-ingesta.
- **tsvector 'simple'**: el corpus mezcla ES/EN. 'spanish' estemiza mal el inglés; la rama léxica
  sirve sobre todo para códigos exactos (AR-1004, 8D-2025-014), que 'simple' conserva. La morfología
  la cubre la rama semántica. Test `test_tsv_simple_keeps_part_codes`.
- **Migraciones por runner, no por `docker-entrypoint-initdb.d`**: initdb solo corre con el volumen
  vacío (no aplicaría a la BD actual ni a migraciones 002+) y no deja registro. Además, añadir un mount
  al servicio `db` provocaría que el siguiente `docker compose up` recreara el contenedor que está
  usando otro agente. No se toca `docker-compose.yml`. **Desviación del DoD** ("aplicada por
  docker-compose"): la instalación limpia es `docker compose up -d db` + `uv run python -m solaris.db.migrate`
  + `uv run python -m solaris.rag.acl`. Si product/wiki lo prefieren, más adelante un servicio one-shot
  `migrate` en compose puede ejecutar el mismo runner.
- Migración aplicada al contenedor en marcha **sin reiniciarlo**: `Aplicadas: 001_rag`; segunda
  ejecución `Aplicadas: ninguna`. `rag.folder_acl` sincronizada con 24 filas. `rag.documents`/`chunks`
  quedan con 0 filas tras los tests.
- El guard de red de `conftest.py` (monkeypatch de `socket`) no afecta a libpq; en el módulo se anula
  explícitamente y los tests de BD solo corren contra 127.0.0.1/localhost.

## Para M2-T3/M2-T5
- La ingesta debe usar un upsert por (doc_id, version) comparando sha256; los chunks, por (doc_id, version, chunk_no).
- La recuperación debe partir **siempre** de `rag.visible_chunks(%(role)s)`; nunca `FROM rag.chunks` directo.
  Con HNSW y filtro, `SET LOCAL hnsw.iterative_scan = strict_order` (pgvector 0.8) evita devolver menos de k resultados.
- `chunks.page` admite NULL (xlsx): la cita de un AMFE usa `fmea_rows.row_no`.

## Puntos para security
1. **El rol es un parámetro de la función**: la garantía ACL depende de que el backend lo derive del usuario
   autenticado (acl.json `users` → role) y de que nunca venga del LLM ni del cuerpo de la petición. Revisar en M2-T5/M4-T1.
2. **No hay RLS ni rol de BD restringido**: el backend se conecta como `solaris` (superusuario del contenedor)
   y cualquier `SELECT FROM rag.chunks` directo se salta la ACL. Propuesta para M3-T1/M4: un rol `solaris_app`
   con solo EXECUTE sobre `visible_*` (o RLS con `current_setting('solaris.role')`), y un test que prohíba `FROM rag.chunks` en `solaris/rag/retrieve*`.
3. Deny-by-default verificado: un rol NULL, vacío, desconocido o con inyección (`calidad' OR '1'='1`) ve 0 filas,
   y una carpeta sin ACL es invisible incluso para admin.
4. `sync_folder_acl` borra y reinserta en una transacción: un fallo a mitad no deja la tabla vacía. Hay
   que confirmar que la ingesta (M2-T3) excluye `acl.json`, `PLANT.md`, `erp/` y `app/evals/` (PAT-004).
5. Secretos: `database_url` y `postgres_password` son SecretStr; la contraseña no se interpola en URL.
   `.env.example` sigue con `DATABASE_URL=...<POSTGRES_PASSWORD>...`: si se copia literal, falla la
   autenticación. Conviene dejarla comentada.
6. El runner ejecuta SQL de ficheros del repo (confianza = contenido versionado); el sha256 detecta ediciones de migraciones ya aplicadas.
